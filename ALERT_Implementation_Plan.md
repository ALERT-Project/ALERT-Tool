# ALERT Tool — Implementation Plan

**Date:** 1 August 2026
**Companion to:** `ALERT_Risk_Rule_Decisions.md` (the *what* and *why*; this is the *how* and *when*)

Seven batches, ordered so that nothing which changes clinical behaviour ships before there is
something in place to detect the change.

---

## Batch 0 — Safety net

**Goal:** be able to see what a change does before it reaches a ward.

Nothing else in this plan is safe without it. There are ~850 lines of clinical branching in
`logic.js`, no tests, and `npm test` currently exits 1.

### The obstacle

`computeAll()` can't be tested as it stands — it reads the DOM through `getState()`, writes
results back to the DOM, and a few rules query elements directly mid-evaluation
(`$('intubatedReason')`, `$('dialysis_type')`).

### Approach — golden master, synthetic data only

No instrumentation is added to the tool and no patient data is collected at any point. See
*Absolute constraint* below.

1. **Build ~40 synthetic patients by hand.** Invented numbers, covering every rule and the
   combinations that matter — CAT 1/2/3, pre and post stepdown, each mitigator on and off.
   Realism informed by de-identified summaries (numbers and ticked gates only, no prose).
2. **Record the current engine's output** for all 40 in a headless browser, exactly as it
   behaves today, bugs included. That is the baseline.
3. **Extract a pure rule engine.** Move rule evaluation into `evaluateRisks(state)` returning
   `{red, amber, suppressed, cat, flaggedIds, checkItems}`. `computeAll()` keeps all DOM
   reading and writing around it. Move the two mid-rule DOM reads into `getState()`.
   **Pure code movement — zero logic edits in this step.**
4. **Verify:** all 40 reproduce byte-identically, or it isn't done.

Batches 1 and 2 then flip specific expected values deliberately. Anything else that moves is a
bug.

### Why this earns its place

The fixture set lives in the repo, is reproducible, and depends on no collection period. The
pure engine is also the artefact you'd hand to any future platform build — the rules without
the interface, which is the thing that couldn't be migrated last time.

**Size:** large. The biggest single piece of work in the plan, and the only one that is pure
engineering with no clinical decision in it.

### Sign-off artefact — local comparison mode

A dev-only mode inside the tool that runs the old and new rule sets side by side on whatever
is currently entered, and reports the difference:

```
Old: CAT 2   →   New: CAT 3
Moved by: albumin <20 removed
```

Sit with a stack of your own reviews, click through twenty, and count. **Everything stays in
the browser** — nothing transmitted, nothing persisted beyond the session, identical data
posture to the tool itself.

That produces the number for the team meeting — the actual effect on your list, generated by
you, rather than a description of the changes.

### Canary

Ship behind a fortnight of CNS feedback: anyone who disagrees with a category flags it. Cheap,
and it surfaces disagreement while it's still easy to reverse.

**Size:** medium.

## Cross-cutting

### Absolute constraint — no data leaves the browser

The tool is a browser-based calculator that transmits nothing, and every batch in this plan
must preserve that. No telemetry, no analytics, no logging hook, no crash reporter, no
external asset, however temporary or well-intentioned.

Verified clean as of 1 August 2026:

- No `fetch`, `XMLHttpRequest`, `sendBeacon`, WebSocket or `EventSource` in `src/` or
  `plugins/`
- All assets local, including the self-hosted Inter font — no CDN, no external stylesheet
- Only outbound URL is the REDCap survey, opened on explicit user click, carrying no
  identifiers: site, ward code, ADDS, category, shift, date (`plugins/redcap.js:128`)
- `sessionStorage` only — clears on tab close. No `localStorage` anywhere

Re-run this check before each batch merges:

```
grep -rn 'fetch(\|XMLHttpRequest\|sendBeacon\|WebSocket\|EventSource\|axios' src/ plugins/ index.html
grep -rno 'https\?://[^"'"'"' )]*' src/ plugins/ index.html
```

Any fixture data committed to the repo must be synthetic. De-identified material supplied for
realism (numbers and ticked gates, no prose, no dates, age as a band) informs the fixtures but
is not itself committed.

### Registration gotcha

Any new input must be added to the right array in `config.js` (`staticInputs`,
`segmentedInputs`, `toggleInputs`, `selectInputs`) or it will render fine and then silently
fail to save, restore or reach the rules. This affects the bloods date, INR/APTT targets, and
the LOS mitigator.

### Build and deploy

- `npm run build` bundles `src/js/main.js` → `dist/bundle.js`.
- **`dist/` must stay committed** — the site is served from the repo (`.nojekyll` present), so
  an uncommitted bundle means the deployed tool doesn't match the source.
- Both `dist/bundle.js` and `dist/bundle.js.map` are currently dirty alongside every source
  file. Worth landing the working tree clean before Batch 0 starts.

### Versioning

Two schemes are live: `package.json` says 1.0.4, `style.css` header says A8.03. Worth picking
one and putting it in the footer so a CNS can tell you which version they're looking at when
they report something.

### Per batch

Rebuild → changelog entry in the existing `ALERT_Changelog_*.md` style → commit on a branch off
`main` → merge after sign-off. Rollback is revert plus rebuild.

## Suggested order

**0 → 1 → 2 → 5 → 3 → 4**

Batch 5 pulled forward ahead of the trend work: it's the change your users will actually
notice and appreciate, it carries no clinical risk, and it gives the team something visible
while Batch 2 is still in its canary fortnight.
